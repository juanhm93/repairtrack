# SPEC-01.1 — Listar, editar y borrar tickets

## Objetivo

Cerrar el resto del PRD §6.2 que el spec 01 dejó fuera: el técnico ve **todos sus** tickets en un listado, abre el detalle, edita los datos del equipo/cliente y puede borrar un ticket.

El spec 01 ya entregó crear, ver (`Show`) y cambiar estado. Esos dos últimos siguen en **llamados distintos**: `GET /tickets/{ticket}` para ver, `PATCH /tickets/{ticket}/status` para el estado. Este spec no los fusiona. Agrega `index`, `edit`/`update` y `destroy`.

El dashboard filtrable (pendientes, atrasados, rangos de fecha) sigue siendo el spec 04. Este listado es la bandeja de gestión de tickets, no el dashboard.

## Dependencias

- Spec 01 implementado: `RepairTicket`, `Customer`, `TicketStatus`, `TicketService::create` / `changeStatus`, `RepairTicketPolicy`, `TicketController` (create/store/show/updateStatus), páginas `tickets/Create` y `tickets/Show`
- Auth Fortify + `AppLayout` + Wayfinder
- Sidebar: [`resources/js/components/AppSidebar.vue`](../../resources/js/components/AppSidebar.vue)
- Componentes de formulario del spec 01: `CustomerFields`, `SuggestInput` (fotos **no** se editan aquí)
- Seeder del spec 01: tickets de demo para `test@example.com`

No depende del spec 02, 03 ni 04.

## Alcance

- `GET /tickets` — listado paginado de los tickets del usuario (todos los estados, incluidos `delivered`)
- Acciones desde el listado: ver, editar, eliminar
- `GET /tickets/{ticket}/edit` + `PUT /tickets/{ticket}` — editar datos del ticket y del cliente; **no** cambia el estado
- `DELETE /tickets/{ticket}` — borrar ticket (con confirmación)
- `TicketService::update` y `TicketService::delete`
- Policy `delete`; `view` / `update` ya existen
- Nav “Tickets” → `tickets.index`
- En `Show`: enlaces a editar y eliminar (el cambio de estado permanece en el PATCH actual)
- Tests

## Fuera de alcance

- Filtros completos del dashboard, indicador de atrasados, foco en pendientes (spec 04)
- Cambiar el estado desde el formulario de edición (sigue el PATCH de spec 01 en `Show`)
- Editar o reemplazar fotos después de crear el ticket (igual que spec 01)
- Envío de correo al editar o borrar (spec 02 solo engancha create y changeStatus)
- Ruta pública `/t/{token}` (spec 03); al borrar, el token deja de resolver (404) porque el ticket ya no existe
- Soft deletes
- Borrado masivo
- Borrar el `Customer` aunque no le queden tickets
- Historial dedicado por cliente (PRD §8)
- Módulo de clientes aparte

## Modelo de datos

Sin tablas nuevas. Sin columnas nuevas.

Al borrar un `RepairTicket`:

- `ticket_status_history` y `ticket_photos` ya hacen cascade delete (spec 01)
- Borrar también los archivos del disco `public` (`tickets/{user_id}/{ticket_id}/…`)
- El `Customer` **no** se borra
- `public_token` desaparece con el ticket

La edición de campos **no** escribe en `ticket_status_history`. Solo `changeStatus` (spec 01) appende historial.

## Backend

### Servicio — `app/Services/TicketService.php`

Extender el servicio del spec 01. Las mutaciones siguen pasando por aquí.

```
paginateForIndex(User $user, array $filters, int $perPage = 15): LengthAwarePaginator
  - where user_id = $user->id
  - with customer
  - filtros opcionales:
      status  → exact match TicketStatus
      q       → LIKE sobre customers.name, customers.email, customers.phone
  - default: todos los estados (incluido delivered)
  - orden: received_at desc, id desc
  - no incluir history ni photos en cada fila

update(RepairTicket $ticket, User $actor, array $data): RepairTicket
  - find-or-create Customer por (user_id del actor, email), igual que create
    - si existe: actualizar name/phone si vinieron
    - reasignar ticket.customer_id a ese customer
  - actualizar campos del ticket: device_type, brand, model, serial_number,
    reported_issue, estimated_cost, received_at, estimated_delivery_at
  - no tocar status, public_token, user_id, fotos
  - transacción
  - no notificar

delete(RepairTicket $ticket, User $actor): void
  - borrar archivos de ticket.photos en disco public
  - $ticket->delete() (cascade history + photos)
  - transacción
  - no notificar
```

No reutilizar el query del spec 04 (`TicketQueryService` / atrasados). Si 04 aún no existe, este listado no lo espera.

### Scoping

- Policy: agregar `delete` — mismo criterio que `view`/`update` (`ticket.user_id === user.id`)
- `index` no necesita un ticket concreto; la query siempre `where('user_id', $user->id)`
- Route model binding scoped al usuario (ya en spec 01). Ticket de otro user → 404
- Un usuario no puede ver, editar ni borrar tickets de otro (404/403)

### Controller — `app/Http/Controllers/TicketController.php`

Agregar al controller del spec 01:

```
index   → Inertia tickets/Index (paginator + filters + statusOptions)
edit    → Inertia tickets/Edit (ticket + customer, customers, deviceCatalog, deviceHistory, statuses no hace falta)
update  → TicketService::update → redirect tickets.show + toast
destroy → TicketService::delete → redirect tickets.index + toast
```

`show` y `updateStatus` no cambian de contrato. `Show` sí gana acciones de UI (editar / eliminar) que pegan a estas rutas.

### Form Requests

`IndexTicketRequest` (o validación liviana en el controller):

- `status` nullable|valor de `TicketStatus`
- `q` nullable|string|max:100

`UpdateTicketRequest`: mismas reglas de campos que `StoreTicketRequest` **sin** `photos` / `photos.*`. El estado no va en este request.

```
Cliente: customer_name requiredIf no existe ese email en el user, customer_phone nullable, customer_email required|email
Equipo: device_type required, brand/model/serial_number nullable
reported_issue required
estimated_cost nullable|numeric|min:0
received_at required|date
estimated_delivery_at nullable|date|after_or_equal:received_at
```

Reutilizar la lógica de `payload()` / find-or-create del store. No aceptar `status`.

En [`routes/web.php`](../../routes/web.php), grupo `auth` + `verified`, junto a las del spec 01:

## Tests

`tests/Feature/Tickets/` (extender `TicketTest` o archivo hermano), `RefreshDatabase`:

- Guest no accede a index/edit
- User autenticado ve en index solo tickets de su `user_id`
- Index lista `delivered` por defecto (a diferencia del dashboard)
- `?status=` y `?q=` filtran
- Edit carga el ticket propio y el formulario
- Update persiste campos del ticket y reutiliza/crea customer por email igual que store
- Update **no** cambia `status` ni `public_token` aunque vengan en el payload
- Update no escribe una fila nueva en `ticket_status_history`
- User A recibe 404 al editar/actualizar/borrar ticket de user B
- Destroy borra ticket, history, photos en DB y archivos en disco; el customer permanece
- Destroy redirige a `tickets.index`
- Show sigue pudiendo cambiar estado por `PATCH .../status` (regresión spec 01)
- Guest / otro user no pueden DELETE

No testear mail ni `/t/{token}` ni filtros de atrasados.

## Criterios de aceptación

- Desde el sidebar se abre el listado de **todos** los tickets del usuario
- Desde una fila se puede ver, editar o borrar
- Ver sigue siendo `Show`; cambiar estado sigue siendo el PATCH de spec 01, no el PUT de edición
- Editar corrige cliente/equipo/problema/fechas/costo sin mover el estado ni mandar correo
- Borrar pide confirmación, quita el ticket y sus fotos/historial, y no toca al cliente
- Un usuario no ve, edita ni borra tickets de otro
- El dashboard del spec 04 no se implementa aquí y este listado no intenta reemplazarlo
